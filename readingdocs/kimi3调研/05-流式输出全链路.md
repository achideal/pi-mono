# 重点 05：流式输出全链路

> **一句话亮点（简历可直接用）**：设计并打通了从 LLM token 到用户屏幕的五级流式链路——provider 流式回调 → 消息总线帧编码 → bot 进程 SSE → Redis PubSub 中转 → admin SSE 转发 → 前端分段渲染；统一了 text_delta / tool_start / tool_args_delta / tool_done / reasoning_delta 等事件协议，实现文本逐字、工具卡片实时、思维链独立成帧的完整打字机体验。

## 为什么这是一个值得重点介绍的难点

"流式输出"在 demo 里就是 LLM SDK 传个 `stream=True`，但生产级 Agent 系统的流式链路要难得多，难在三点：

1. **链路长且跨语言**：token 从 Python 的 LLM provider 产生，穿过 bot 进程的 HTTP SSE、engine server 的 Redis 发布、Go admin 的 SSE 转发，最后到 TypeScript 前端渲染——五级跳转，任何一级丢帧、乱序、格式不兼容，用户看到的就是"卡住"或"花屏"；
2. **不只是文本**：Agent 一轮回复里混着正文 token、工具调用开始/参数增量/完成、思维链（reasoning）、执行日志、轮次边界。这些事件必须**独立成帧、交错有序**，否则思维链会被当正文渲染、工具参数会拼接错乱；
3. **部署不原子**：bot 子进程和 engine server 是独立部署的，线上必然存在"新 bot + 旧 server"的部分部署窗口——协议升级必须向前向后兼容，不能直接换格式。

本项目的答案是一套显式的帧协议 + 逐级的容错设计。本文按 token 的旅程逐级剖析。

## 先备知识：本文涉及的术语与变量

| 术语/变量 | 含义与示例 |
|---|---|
| **token** | LLM 流式输出的最小文本片段，如 `"你好"`、`"，"`。provider 每产出一个就回调一次 `on_token`。 |
| **on_token / on_tool_start / on_tool_args / on_reasoning** | engine provider 层的四个流式回调（`engine/nanobot/providers/litellm_provider.py:264-267`）。任一非 None 即进入流式模式（`:335-341`）。 |
| **chunk / delta** | LLM SSE 流中的一个数据块。`delta.content` 是文本，`delta.tool_calls` 是工具调用增量——注意工具调用的 name/arguments 也是**流式**到达的，参数 JSON 是逐字拼出来的。 |
| **消息总线 / bus / OutboundMessage** | engine 内解耦渠道与 Agent 的事件总线。Agent 产出的每个流式事件被包成 `OutboundMessage`（含 channel、chat_id、content、metadata）发布，由 HttpChannel 转成 SSE 帧。 |
| **_bus_token / _bus_progress** | AgentLoop 内两个闭包（`engine/nanobot/agent/loop.py:4276, 4159`），把 token 和进度事件发布到总线。`_bus_token` 打 `_stream_token` 元数据；`_bus_progress` 按类型打 `_tool_hint` / `_tool_events` / `_reasoning_delta` 等元数据。 |
| **帧 / 事件类型** | 链路上的标准化事件：`text_delta`（文本增量）、`tool_start`（工具开始）、`tool_args_delta`（参数增量）、`tool_done`（工具完成）、`tool_progress`（执行日志）、`reasoning_delta`（思维链）、`round_complete`（轮次边界）、`task_done`（任务终态）。 |
| **toolIndex** | turn 内全局工具序号。前端按它（而非工具名）匹配工具卡片——同一工具在一轮里可能被调用多次，名字会撞，序号不会（根 `CLAUDE.md` web 架构要点）。 |
| **_collect_from_bot** | engine server 侧函数（`engine/nanobot/server/server.py:3715`）：消费 bot 进程的 `/api/chat` SSE，把事件发布到 Redis PubSub 频道。 |
| **_pub** | `_collect_from_bot` 内的安全发布闭包（`server.py:3952-3982`）：带断线重连与指数退避（1s/2s/4s，上限 5s）。 |
| **consumeSSE** | 前端 SSE 解析器（`web/src/composables/useChat.ts:99-134`）：手动读 `ReadableStream`，按行切 `data: ` 帧，可选读超时（Room 链路 35s）。 |
| **segments** | 前端消息模型：一条 bot 消息 = 有序的 segments 数组，文本块（`type:'text'`）与工具卡片（`type:'tool'`）按到达顺序交错排列。流式渲染就是不断往这个数组追加/更新。 |
| **_applyChunk** | Room 链路的帧分派函数，把 chunk 按类型路由到 chatStore 的对应 action；DM 链路不走它，由 useDMPush 的事件循环直接分派（`web/doc/03-chat-messaging.md:75-79`）。 |

### 第一级：provider 流式回调（token 的诞生）

provider 层用 LiteLLM 统一接入多家 LLM，流式核心在 `_chat_stream`（`litellm_provider.py:394-436`）：逐 chunk 读上游 SSE，文本走 `await on_token(token)`（`:478-483`），工具调用**按 index 累积**——`tool_acc` 字典以 `tc_delta.index` 为键拼 id/name/arguments，工具名首次出现触发 `on_tool_start`，参数增量触发 `on_tool_args`（`:485-509`）。思维链走独立的 `on_reasoning` 回调，与正文分两路累积（`:427-433` 注释："思维链一旦混进正文，就会被当作回答渲染进气泡"）。流结束后用 `json_repair` 容错解析可能不完整的参数 JSON。

一个值得注意的设计：是否流式由"是否传了回调"决定（`:335-341`），连只订阅思维链也强制走流式——因为思维链恰好产生在正文前的静默期，非流式拿到完整结果时"实时"已无意义。

### 第二级：消息总线帧编码（事件的分类打包）

AgentLoop 把 provider 回调接到总线上（`loop.py:4386-4387`：`on_progress=on_progress or _bus_progress, on_token=_bus_token if not on_progress else None`）。`_bus_token` 逐 token 发 `OutboundMessage`（`loop.py:4276-4283`）；`_bus_progress` 按事件类型打不同的 metadata 标记（`loop.py:4159-4274`）。

这里藏着全链路最精彩的兼容性设计——**tool_events 双发**（`loop.py:4172-4191` 注释）：hook 重构后工具事件打包成新契约 `toolEvents` 数组（带 toolIndex/arguments/result/phase），但线上存在新旧代码部分部署的窗口：新 bot + 旧 server 时 tool_start 会完全消失；旧 bot + 新 server 时拿不到 tool_done。解法是携带 tool_events 时**同时发两帧**——一条 legacy `_tool_hint` 兜底、一条新契约 `_tool_events`，下游 `_collect_from_bot` 用 `_tool_seen_idx` 集合按 toolIndex 去重，哪一路先到注册哪个，另一路到达跳过。前端工具卡片绝不重复创建。

轮次边界帧 `round_complete` 与思维链帧 `reasoning_delta` 都**独立成帧**走 `_raw` 直转分支（`loop.py:4196-4227`），前者让前端把当前气泡封口、为下一段开新气泡，使 client/server 消息粒度一致；后者防止思维链混入正文。

### 第三级：Redis 中转（`_collect_from_bot` + `_pub`）

engine server 消费 bot 的 SSE 并转发布（`server.py:3715`）。发布闭包 `_pub` 的容错设计（`server.py:3952-3982`）：publish 内部有断线重连后重试一次；连续失败时按 1s/2s/4s（上限 5s）指数退避，退避期事件**直接丢弃**（打 debug 日志），一旦成功立即重置退避——宁可丢帧也不让 Redis 抖动拖垮 bot 的任务执行。丢帧的正确性由 JSONL 落盘 + 前端 history 补洞兜底（见重点 20/23）。

### 第四级：admin SSE 转发

admin 的 `DMSubscribe`/`RoomSubscribe` 把 Redis 频道消息原样写进 SSE 流（`admin/internal/api/chat_handler.go:1557`），同时旁路扫描每条消息做指标采集（usage 异步入库），并在订阅建立时下发 `subscribed` 哨兵（见重点 20）。Redis 不可用时降级为直接代理 engine 的 SSE（`chat_handler.go:1587-1598`）——**每一级都有降级路径**。

### 第五级：前端分段渲染

前端 `consumeSSE`（`useChat.ts:99-134`）不依赖 EventSource 而是手动读 `ReadableStream`：按 `\n` 切行、只取 `data: ` 前缀行、缓冲区留尾（`buf = lines.pop()`）处理半行帧，可选 `readTimeout`（35s）防假死。DM 链路的事件分派在 useDMPush 循环里（`useChat.ts:2183-2228`）：

- `text_delta` → `_ensureMsg` 找到/领养气泡 → `appendBotText`（含重叠去重，见重点 23）追加到当前 text segment；
- `tool_start` → 先把上一个工具 `completeLastToolCall` 封口，再 `addToolCall` 新卡片，`toolCount` 按 engine 全局 toolIndex 同步（`useChat.ts:2191-2202`）；
- `tool_args_delta` / `tool_done` → 按 toolIndex 精确匹配 segment（`stores/chat.ts:1307-1312`：先按 `tool.index` 精确匹配，回退数组下标兼容老数据）更新参数与完成态。

最终渲染模型是 segments 交错数组：用户看到的是"文字 → 工具卡片（参数实时滚动）→ 文字"的混合流，与 Agent 实际执行顺序严格一致。

## 关键设计决策与权衡

1. **帧协议显式化**：事件类型字段 + 独立成帧，而不是把控制信息混进文本流（如特殊标记符）。显式协议的解析可靠性和可演进性远超隐式约定。
2. **双发兼容优于强制同步部署**：新旧两帧 + 下游去重，用带宽换部署自由度——多进程架构下"所有进程同一版本"是不可达成的假设。
3. **toolIndex 而非工具名匹配**：同名工具一轮内多次调用是常态（如多次 read_file），只有序号能唯一锚定。
4. **逐级降级**：provider 可无回调非流式、Redis 挂了 admin 直连代理、SSE 断了有 history 补洞——每一级都假设下一级会失败。
5. **思维链独立通道**：thinking 模型的推理过程是产品特性（可折叠展示）而非正文，协议层面就分开，不靠前端正则剥离。

## 面试话术（怎么讲）

> 我们的流式链路是五级结构：Python provider 层逐 chunk 回调 on_token/on_tool_start/on_tool_args，AgentLoop 通过消息总线把事件编码成带类型标记的帧，bot 进程出 SSE，engine server 消费后经 Redis PubSub 中转，Go admin 再转成 SSE 给前端，前端 consumeSSE 逐行解析后按帧类型分派到 store 的分段模型——文本块和工具卡片交错排列。难点在三个地方：一是协议设计，文本、工具参数增量、思维链、轮次边界都必须独立成帧，否则思维链会被当正文渲染；二是部署兼容，bot 和 server 独立部署，线上必然有新旧并存的窗口，我对工具事件做了新旧双帧同发加下游按 toolIndex 去重；三是容错，Redis 发布失败时指数退避并允许丢帧，正确性由 JSONL 落盘和前端 history 补洞兜底，链路每一级都有降级路径。

## 可能的追问及答案

**Q：为什么中间要过 Redis PubSub，直连不行吗？**
A：直连意味着 SSE 连接必须落在"跑任务的那个进程"上，违背读写分离架构（重点 20）的目标——刷新恢复、跨容器接收都要求连接与任务解耦。Redis 频道是天然的多对多广播枢纽，也让 admin 能旁路采集指标。

**Q：每 token 一帧，性能扛得住吗？**
A：token 帧很小（几十字节），瓶颈不在带宽而在连接数。真正优化过的是发布侧的容错——`_pub` 在 Redis 抖动时直接丢帧而非堆积重试，保护任务执行主链路；前端侧 segments 是响应式数组，追加是 O(1)。

**Q：工具参数流式增量有什么用？直接等 tool_done 拿全量不行吗？**
A：长参数工具（如 write_file 写几百行代码）的参数生成可能持续十几秒，流式增量让用户实时看到"Agent 正在写什么"，是关键的等待体验。且 exec 类工具的执行日志（tool_progress）本身就是持续输出，等完成再展示就失去了实时性。

**Q：双发两帧会不会让前端重复创建工具卡片？**
A：不会。去重在 engine server 的 `_collect_from_bot` 完成（`_tool_seen_idx` 集合按 toolIndex 注册，先到先得），前端永远只收到一路。即使极端情况两路都到，前端 addToolCall 按 toolIndex 匹配也能幂等吸收。

**Q：如果让你重新设计，会改什么？**
A：会把帧协议加上 schema 版本号字段（现在靠事件类型分支兼容，双发是补丁式兼容），并在链路上统一帧的 envelope（type + payload + meta 三层固定结构），让新增事件类型不需要触碰各级的解析代码——目前的 if 链分派在事件类型增多后认知负担偏高。

## 事实边界

- 本文基于 `application/` 工作区（engine develop 分支，最新提交 2026-07-31；admin 2026-07-28；web 2026-07-21）逐行核实；`digi-pal/` 为 2026-05 中旬旧快照，不作为依据（旧快照中无 `on_reasoning` 回调、无 `round_complete`/`reasoning_delta` 帧，与本文描述不一致，以 `application/` 为准）。
- 本文以 DM 链路为主线；Room 链路在 engine server 内有额外的扇出与链式调用编排（见重点 10），帧协议相同。
- "五级"是逻辑分层，物理上 bot 进程与 engine server 可同 Pod；desktop/vscode-plugin 各有等价的 consumeSSE 实现（代码同源复用）。
- token 级性能描述基于设计分析，非压测数据。
